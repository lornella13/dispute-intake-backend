# Dispute Intake Module — Backend

FastAPI + SQLite backend for Aline's Task B: Dispute Intake Module.
Provides operator login, complaint creation with validation, bank-isolated
complaint queue and detail views, a complaint pre-validation endpoint, and a
local dispute-hub registration mock.

## Architecture

```
React Frontend  <==>  FastAPI Backend  <==>  SQLite (disputes.db)
                                   |
                                   +--> Local Hub Mock (POST /api/v1/customer-disputes)
```

### Layers

| Layer | Responsibility | Key files |
|-------|---------------|-----------|
| Routes | HTTP route definitions, request/response schemas | `src/routers/dispute.py` |
| Controllers | Coordination between routes and services | `src/controllers/dispute.py` |
| Services | Business logic: validation, hub mock, complaint workflow | `src/services/dispute.py`, `src/services/auth.py` |
| Repositories | Raw SQL against SQLite | `src/repositories/dispute.py` |
| Models | Plain Python data classes | `src/models/dispute.py` |
| Schemas | Pydantic request/response models | `src/schemas/dispute.py` |
| Middleware | Request ID tracking | `src/middleware/logging.py` |
| Errors | Custom exceptions + global handler | `core/error.py` |
| Database | SQLite connection + schema init | `database.py` |

## Environment Configuration

Copy `.env.example` to `.env` and fill in the values. The `.env` file is
gitignored and must never be committed.

Required variables:

| Variable | Description | Example |
|----------|-------------|---------|
| `OP_GREEN_USERNAME` | Greenbank operator username | `aline_green` |
| `OP_GREEN_PASSWORD_HASH` | PBKDF2-HMAC-SHA256 hash of password | see below |
| `OP_GREEN_BANK` | Greenbank bank name | `Greenbank` |
| `OP_BLUE_USERNAME` | Bluemobile operator username | `brian_blue` |
| `OP_BLUE_PASSWORD_HASH` | PBKDF2-HMAC-SHA256 hash of password | see below |
| `OP_BLUE_BANK` | Bluemobile bank name | `Bluemobile` |
| `JWT_SECRET_KEY` | Secret for signing access tokens | `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `JWT_ALGORITHM` | Token signing algorithm | `HS256` |
| `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` | Token expiry in minutes | `30` |

Generate a password hash:

```bash
python3 -c "
import hashlib, os, base64
salt = base64.b64encode(os.urandom(16)).decode()
h = hashlib.pbkdf2_hmac('sha256', b'your_password', base64.b64decode(salt), 100000)
print(base64.b64encode(h).decode() + '\$' + salt)
"
```

## API Endpoints

### Authentication

**POST /auth/login**
- Auth: None
- Body: `{ "username": "string", "password": "string" }`
- Success (200): `{ "access_token": "string", "token_type": "bearer", "bank": "string" }`
- Error (401): `{ "error_code": "AUTH_FAILED", "message": "..." }`

### Complaints

**POST /complaints/validate**
- Auth: Bearer token required
- Body: `ComplaintCreateSchema`
- Success (200): `{ "valid": true, "message": "Complaint data is valid." }`
- Error (400): `{ "error_code": "VALIDATION_FAILED", "message": "..." }`
- Side effects: None — no complaints or audit records created

**POST /complaints**
- Auth: Bearer token required
- Body: `ComplaintCreateSchema`
- Success (200): `ComplaintSuccessEnvelope` — `{ "complaint_id": "string", "registration_status": "string", "hub_claim_id": "string|null", "request_id": "string" }`
- Error (400): `{ "error_code": "VALIDATION_FAILED", "message": "..." }`
- Persists: complaint row + audit log row

**GET /complaints**
- Auth: Bearer token required
- Success (200): `List[ComplaintResponseSchema]` — array of complaint objects filtered by operator's bank

**GET /complaints/{id}**
- Auth: Bearer token required
- Success (200): `ComplaintResponseSchema`
- Error (404): `{ "error_code": "COMPLAINT_NOT_FOUND", "message": "..." }` — also returned when the complaint belongs to a different bank (cross-bank isolation)

### Health

**GET /health**
- Auth: None
- Success (200): `{ "status": "healthy", "timestamp": "string", "environment": "string" }`

### Local Hub Mock

**POST /api/v1/customer-disputes**
- Auth: None (public mock of shared dispute service)
- Body: `{ "transfer_reference": "string" }`
- Success (200): `{ "status": "REGISTERED", "claim_id": "CLM-xxxxxx", "message": "Success" }` — for references NOT ending in `999`
- Rejection (200): `{ "status": "REJECTED", "claim_id": null, "message": "Scheme violation: Exceeded bounds." }` — for references ending in `999`
- Persists: None — no complaint or audit records created

## Validation Rules

| Field | Rule |
|-------|------|
| `transfer_reference` | Must match `^TXN-\d{6}$` (e.g. `TXN-100293`) |
| `amount` | Non-empty, positive decimal string (e.g. `"15000"` or `"15000.50"`). Zero, negative, and malformed values rejected. |
| `currency` | Max 3 chars, default `"RWF"` |
| `category` | One of: `debited_not_credited`, `wrong_recipient`, `duplicate`, `scam` |
| `description` | Optional string (max 2000 chars recommended by frontend) |
| `evidence` | Optional string (filename reference only — no file upload). Required for `wrong_recipient` and `scam` categories. |

## Evidence Limitations

The `evidence` field stores only a filename (string). There is no file upload
endpoint. The frontend file picker captures `file.name` and stores it as a
string reference; the actual file is never transmitted to or stored by the
backend.

## Hub Mock Behavior

- Accepts any `transfer_reference` that does **not** end in `999` → `REGISTERED` with synthetic `CLM-<8-hex>` claim ID
- Rejects references ending in `999` → `REJECTED` with `claim_id: null`
- No external service calls; entirely local
- No complaint or audit records created by the mock itself

## Security Assumptions

- **Passwords**: Stored as PBKDF2-HMAC-SHA256 hashes (100k iterations) in environment variables. Never plain text in source.
- **Tokens**: HMAC-SHA256 signed JWT-like tokens with configurable expiration (default 30 min). Signature, expiry, and required claims (`sub`, `bank`) validated on every protected request.
- **Bank isolation**: Operator's bank is derived server-side from the signed token, never from request body. Complaint list and detail endpoints filter by `bank = authenticated_user.bank`. Cross-bank reads return `404`.
- **Request IDs**: `SecurityTrackingMiddleware` generates/propagates `X-Request-ID`; echoed in response headers.
- **Error responses**: `{ "error_code": "...", "message": "..." }` — no stack traces or internal details exposed.
- **Audit trail**: `audit_logs` table records `id, request_id, operator_username, bank, action, target_id, timestamp`. No secrets stored.
- **Token storage**: Frontend stores bearer token in `localStorage`. This is vulnerable to XSS. HttpOnly cookies would be more secure but require backend cookie support not present in this architecture.
- **Configuration fail-safe**: If `JWT_SECRET_KEY` or operator credentials are missing, the app raises `RuntimeError` on first use rather than running insecurely.

## Database Schema

### `complaints` table

| Column | Type | Notes |
|--------|------|-------|
| id | TEXT PK | `CMP-<6-hex>` |
| bank | TEXT NOT NULL | Operator's bank (Greenbank / Bluemobile) |
| operator_username | TEXT NOT NULL | Authenticated operator |
| transfer_reference | TEXT NOT NULL | `TXN-XXXXXX` format |
| amount | TEXT NOT NULL | Decimal string |
| currency | TEXT NOT NULL | Default `RWF` |
| category | TEXT NOT NULL | One of 4 categories |
| description | TEXT | Private operator notes |
| evidence | TEXT | Filename reference only |
| registration_status | TEXT NOT NULL | `REGISTERED` / `REJECTED` |
| hub_claim_id | TEXT | Synthetic claim ID or null |
| hub_error_message | TEXT | Error detail on rejection |
| created_at | TEXT NOT NULL | ISO timestamp |

### `audit_logs` table

| Column | Type | Notes |
|--------|------|-------|
| id | TEXT PK | UUID |
| request_id | TEXT NOT NULL | Correlates with X-Request-ID |
| operator_username | TEXT NOT NULL | Who performed the action |
| bank | TEXT NOT NULL | Operator's bank |
| action | TEXT NOT NULL | e.g. `CREATE_COMPLAINT` |
| target_id | TEXT | Complaint ID acted upon |
| timestamp | TEXT NOT NULL | ISO timestamp |
